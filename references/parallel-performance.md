# 并行、恢复和验证预算

## 两层并行，不是同仓多人乱写

- 主控：读下游、选不同业务、整批spec/历史预检、分配唯一编号、维护清单/结果。
- 仓库worker：默认2～4个；一仓一个独占容器，负责实现、题位、一轮整体测试与集中修复。分配好第一仓就启动worker；主控继续准备下一仓。
- 流水线：`--jobs` 默认最多4；`--probe-jobs 2` 防止多个npm/Maven/服务挤爆内存；`--publish-jobs 1` 避免同时建仓。资源紧张时自动减并发，不省略启动联通。
- 默认compact布局只保留一个共享前端和一套通用API，避免18套同构页面/路由放大后续任务的源码扫描和上下文成本。
- 同父目录仍只运行一个批次主控；父目录总锁防其他流水线竞争，批次内部worker可并行。scaffold分配编号临界区串行，登记册保留文件锁；不要再要求“并行必须换父目录”。
- 进度由主控汇总阶段开始/结束和耗时，不在每条日志等用户批准。可以用工具会话/异步agent持续工作，不必强制单一前台长阻塞。

## 验证预算：每仓1次测试、至多1次修复、1次最终smoke

| 时机 | 做什么 | 不做什么 |
|---|---|---|
| 设计/实现 | 领域/相似度预检、候选可行性、编写关键链路断言 | 不写一个模块就全量测试，不先建远端 |
| 一次整体测试 | 一次运行已有自动化测试、主要数据链路断言、必要类型/编译；汇总静态/容量/查重与独立review问题 | 不边测边改，不自动retry失败测试，不额外手工逐页验收 |
| 一次集中修复 | 一次性处理清单、更新源码和受影响题位证据，提交最终源码 | 不按每个根因再修3轮，不重复整体测试/E2E/构建 |
| 最终启动联通 | 干净clone、并行装依赖、后端health、前端HTML/入口、代理health、清理 | 不遍历全业务接口，不运行Playwright，不跑生产build |
| 发布/网络重试 | 核对最终HEAD、启动联通/查重证据与容量/远端 | 不因GitHub网络错误重装依赖/重跑测试 |

首次整体测试可以包含E2E或构建，但每个命令只执行一次，且不强制额外添加整套浏览器遍历。新增数据链路用最小真实行为断言覆盖，不只靠脚手架CRUD；无测试时补关键断言，不伪造pass。测试失败先收集其余独立检查结果，然后统一修复。无问题则修复次数为0。

主控在仓外 `verification-round.json` 保存测试基线SHA、命令/退出码、修复清单及0/1轮计数。worker与主控、断点恢复共享同一计数；不把修复前SHA的测试结果写成最终HEAD全量通过。最终smoke失败或最终材料门禁不通过，就保留现场和恢复命令、记录阻塞、继续其他仓，不开启第二轮修复；用户另行要求返修时再作为新任务执行。

容量map固定放`<container>/.s11-meta/repo-topic-map.json`，不提交进源码仓库；其`base_commit`直接等于最终HEAD。源码仓库只保留`.s11-spec.json`和运行代码。

`run_pipeline.py` 只执行最终静态/容量/查重与 `probe_startup.py --clean-clone --profile startup`，不负责首次测试或自动修复。publisher不因没有build/E2E证据拒绝合格smoke，也不把smoke等同于全业务通过。`--profile full`是首次测试的显式工具，不能在最终阶段偷偷开启。

## 缓存与复用原则

- npm采用lock约束的`npm ci`，复用下载缓存并优先离线命中；pip/Maven同样只复用各自下载/构件缓存。禁止复用脏工作树、把宿主node_modules搬进异架构容器、无锁改变依赖解析。
- 默认smoke不检查/下载浏览器；只有显式full才检查已安装浏览器、缺失时安装。依赖缓存错误最多清理本批对应缓存后重试一次，不改源码、不重启整轮测试，不删除其他项目环境。
- **probe不跨运行缓存成功结果**：每次正式probe只实际执行启动联通，报告 `evidence_reused: false` 与 `verification_scope: startup-connectivity`。不复用旧E2E结果来声称修复后全量通过。
- 正式跨环境交付仍在目标环境实际安装和smoke；本机probe成功不代表Linux已验证。
- 每次probe都是fresh；需要基准对照时记录实际wall time，不从日志猜测。不手改报告时间戳、ok或指纹。

## 恢复而不是重造

保存spec→project_id→repo_root及各阶段报告，业务源码提交在main。在原仓保留源码/报告和测试修复计数，不能用重造绕过预算。完整流水线可通过`--prepared-repo`使用原仓，不再scaffold；重新调用pipeline会再做启动联通probe；只用于中断恢复，不用于反复碰运气，不能把`--skip-probe`当恢复发布手段；若只有远端推送失败，直接重跑publisher即可保留同HEAD的已有验收结果。

GitHub创建成功后保存仓外ID归属凭据；恢复同名仓必须匹配真实仓库ID，缺凭据/ID变化均阻塞，不因为远端为空就接管。发布失败时直接重跑publisher并检查真实SHA；不改名接管陌生仓、不强推。首次整体测试后只集中修复一轮，最终失败后记录阻塞并继续其他仓，最终不能把部分通过写成全部完成。

## 测量而非许诺倍数

记录每仓生成/首次测试/集中修复/静态/容量/相似度/安装/启动联通/清理/发布耗时、缓存命中和整个批次wall time；E2E/构建未运行则明确标注，不计作通过。并行能重叠独立工作，但速度取决于依赖缓存、网络和资源；没有同负载端到端实跑对照，不写“快3倍/10倍”。
